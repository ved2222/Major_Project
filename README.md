# Real-Time UAV Telemetry Analysis and Mission Risk Assessment for Tactical Multirotor ISR Operations

## About the Project

This project develops a telemetry-driven system for **Tactical Multirotor ISR (Intelligence, Surveillance and Reconnaissance) UAV operations**.

The system is designed to monitor UAV telemetry, identify abnormal flight behaviour, assess mission risk, and convert complex flight data into meaningful operational insights for mission operators.

The project goes beyond a simple **Normal / Anomaly** classifier. The intended pipeline is:

```text
UAV Telemetry
      ↓
Telemetry Processing
      ↓
Data Synchronization
      ↓
Temporal Feature Engineering
      ↓
Anomaly Detection
      ↓
Anomaly Persistence
      ↓
Subsystem Identification
      ↓
Mission Risk Assessment
      ↓
Explainable Alert
      ↓
Operator Decision Support
```

The proposed platform is intended to improve situational awareness, operator response, mission reliability, and flight safety.

---

## Project Objective

The system is intended to:

1. Collect and analyse telemetry generated by a multirotor UAV.
2. Monitor navigation, motion, power, sensor, estimator, actuator, and system-health parameters.
3. Detect abnormal flight behaviour and potential anomalies.
4. Identify the subsystem associated with abnormal behaviour.
5. Evaluate the potential impact on the mission.
6. Generate a mission risk level.
7. Provide human-readable explanations for alerts.
8. Support operators with decision-support options.
9. Maintain mission history for post-flight analysis and trend identification.

The project objective document describes risk categories such as **Low, Medium, High, and Critical**, along with possible operator actions such as **Continue Mission, Reduce Speed, Return-to-Base (RTB), Emergency Landing, and Hardware Inspection**.

## What Are We Actually Building?

The system aims to answer four operational questions:

```text
What happened?
      ↓
Which subsystem is involved?
      ↓
How persistent/severe is it?
      ↓
What could be the impact on the mission?
```

For example, a combination such as:

```text
GPS uncertainty increases
        +
Satellite behaviour changes
        +
EKF innovation increases
        +
Local-position behaviour changes
```

could be interpreted as evidence of a potential **navigation-related anomaly**.

The anomaly detector therefore acts as the first stage of a larger telemetry-to-risk pipeline.

# Dataset and Telemetry Processing

The current implementation uses **PX4 ULog flight telemetry** from multirotor UAV operations.

The original dataset contains approximately:

- **31 GB** of telemetry data
- Approximately **3,196 ULog files**

The project does not feed the complete raw dataset directly into machine learning. Relevant flights, PX4 topics, and fields are first selected and transformed into a synchronized analytical dataset.

### Processing Pipeline

```text
PX4 ULog Files
      ↓
Select Relevant Flights
      ↓
Select Relevant PX4 Topics
      ↓
Select Required Fields
      ↓
Extract Raw Telemetry
      ↓
Synchronize Multi-Rate Signals
      ↓
Convert to 10 Hz
      ↓
Create 10-Second Windows
      ↓
Merge Flight Data
      ↓
Missing-Value Handling
      ↓
Constant Feature Analysis
      ↓
EDA
      ↓
Feature Engineering
      ↓
Machine Learning
```

The current curated dataset discussed in the project contains approximately:

- **6,201 rows**
- **54 columns**
- **9 flight IDs**
- **10 Hz sampling**
- **10-second temporal windows**
- **No manually assigned anomaly labels**

The exact CSV should be treated as the source of truth if the dataset is regenerated.

---

## Why 10 Hz?

PX4 telemetry topics are recorded at different rates. To analyse signals from multiple subsystems together, the selected telemetry is synchronized to a common rate of **10 Hz**.

Therefore:

```text
1 sample = 100 ms
10 samples = 1 second
~100 samples = 10 seconds
```

This provides a common temporal representation while retaining information about short-duration flight behaviour.

---

## Why 10-Second Windows?

UAV anomalies are often temporal rather than single-point events.

For example:

```text
One unusual GPS measurement
        ≠
Persistent GPS degradation
```

A 10-second window allows the system to study the behaviour of telemetry over time.

The synchronized raw samples are retained. Window identifiers and timestamps provide the grouping required for downstream feature engineering.

# Selected Telemetry Topics

The current compact telemetry set uses:

| PX4 Topic | Main Purpose |
|---|---|
| `battery_status` | Battery voltage, current and remaining capacity |
| `system_power` | Flight-controller power-rail health |
| `vehicle_gps_position` | GPS quality, velocity and satellite information |
| `vehicle_local_position` | Estimated local position and vertical motion |
| `vehicle_attitude` | UAV rotational behaviour |
| `vehicle_attitude_setpoint` | Desired attitude and thrust |
| `sensor_combined` | Raw IMU measurements |
| `sensor_baro` | Barometric pressure and altitude |
| `estimator_status` | State-estimator health and consistency |
| `ekf2_innovations` | Estimator innovation/residual behaviour |
| `actuator_controls_0` | Controller commands |
| `actuator_outputs` | Final actuator outputs |
| `cpuload` | Flight-controller CPU and memory health |

Together, these signals cover navigation, estimation, motion, IMU behaviour, power, control, actuator behaviour, and flight-controller health.

# Unsupervised Anomaly Detection

The current dataset does not contain trusted manual anomaly labels. Therefore, the first machine-learning approach is **unsupervised anomaly detection**.

The planned baseline model is:

### Isolation Forest

The model will learn the structure of normal telemetry behaviour and assign an anomaly score to unusual observations or engineered windows.

```text
Normal Flight Behaviour
        ↓
Learn normal patterns
        ↓
Evaluate new telemetry behaviour
        ↓
Anomaly Score
        ↓
Unusual Window
```

The anomaly score is not the final mission decision. It is the input to persistence analysis, subsystem interpretation, and risk assessment.

# Feature Engineering

Before machine learning, the raw telemetry is converted into temporal features for each 10-second window.

Candidate statistical features include:

- Mean
- Median
- Standard deviation
- Minimum
- Maximum
- Range
- RMS
- First value
- Last value
- Delta/change
- Trend/slope

Domain-specific features will also be developed.

### GPS / Navigation

Possible features:

- GPS uncertainty
- Satellite availability
- Velocity behaviour
- Position changes

### IMU

Possible features:

- Vibration
- Acceleration variability
- Gyroscope behaviour
- Rotational disturbances

### EKF / Estimation

Possible features:

- Innovation magnitude
- Velocity innovation
- Position consistency
- Estimator health

### Battery / Power

Possible features:

- Voltage behaviour
- Current behaviour
- Voltage sag
- Discharge trends

### Actuators

Possible features:

- Output variability
- Actuator imbalance
- Command-to-output differences
- Sustained high actuator demand

# From Anomaly Detection to Explanation

A major goal is to avoid producing an unexplained anomaly score.

The system should connect abnormal telemetry behaviour with the relevant UAV subsystem.

Example:

```text
Anomaly Detected
      ↓
GPS uncertainty increased
      ↓
Satellite behaviour changed
      ↓
EKF innovation increased
      ↓
Local-position behaviour changed
      ↓
Possible navigation-related anomaly
```

The planned **Explainable Analytics Panel** will provide human-readable explanations for why an alert or risk level was generated.

# Mission Risk Assessment

The project extends anomaly detection into **mission risk assessment**.

The proposed risk engine will use categories such as:

```text
LOW
MEDIUM
HIGH
CRITICAL
```

Risk assessment can consider:

- Type of anomaly
- Affected subsystem
- Severity
- Persistence
- Current flight condition
- Potential mission impact
- Combination of multiple abnormal signals

An important design principle is:

```text
Anomaly ≠ Automatically Mission Failure
```

An anomaly becomes operationally meaningful when its persistence, severity, subsystem involvement, and mission consequences are considered.

# Avoiding Data Leakage

Because UAV telemetry is time-series data, random row-wise splitting can allow samples from the same flight to appear in both training and testing.

The project therefore uses a **flight-wise splitting strategy** for machine-learning evaluation.

```text
Flight 1 ─┐
Flight 2 ─┤
Flight 3 ─┤── Training
Flight 4 ─┘

Flight 5 ─┐
Flight 6 ─┤── Testing
Flight 7 ─┘
```

This is intended to provide a more realistic evaluation on previously unseen flights.

---

# Evaluation Strategy

Because the initial dataset has no trusted anomaly labels, supervised accuracy is not the primary evaluation approach.

The project can evaluate:

- Anomaly-score distributions
- Percentage of windows flagged
- Flight-wise consistency
- Temporal persistence
- Visual inspection of anomalous windows
- Agreement with telemetry and estimator-health indicators
- Domain-based interpretation
- Synthetic anomaly injection where appropriate

If reliable labelled anomaly data becomes available later, precision, recall, F1-score and related metrics can be added.
